## Подготовка и порядок команд

Сначала выполнить из корня проекта: `psql -X -h localhost -U student -d olist -v ON_ERROR_STOP=1 -f lab12/lab12.sql`. Создаются `lab.inventory` со 100 наиболее часто встречающимися товарами и `lab.inventory_movements`. Пример атомарного UPDATE внутри файла откатывается.

Открыть два независимых подключения `psql -X -h localhost -U student -d olist`. Команды `session_a.sql` и `session_b.sql` выполнять **блоками**, по таблице ниже. `A01`, `B01` и другие метки находятся в комментариях SQL. Взаимная блокировка намеренно вызывает ошибку; после неё продолжить блоки отката и восстановления.

| Этап | Последовательность блоков |
|---|---|
| Подготовка | A01, B01 |
| Потерянное обновление | A02, B02, A03, B03; результат выводится в начале A04 |
| Блокировка строки | A04, B04 начинает ожидание, A05 освобождает строку, B04 заканчивается, B05; результат в начале A06 |
| Атомарное резервирование | A06, B06 начинает ожидание, A07, завершение B06, B07; результат в начале A08 |
| Неповторяемое чтение | A08, B08, A09 |
| Повторяемое чтение | A10, B09, A11 |
| Фантом | A12, B10, A13 |
| Взаимная блокировка | A14, B11, A15 начинает ожидание, B12; дождаться завершения обоих запросов, A16, B13 |
| Восстановление | B14, A17 |

A01 сохраняет первоначальные `qty` и `version` двух выбранных товаров во временную таблицу сеанса A. B14 удаляет только движение, добавленное в B10. A17 восстанавливает сохранённые остатки и версии. Сеанс A необходимо сохранять открытым до A17.

## Наблюдения

Сеансы имели разные `pg_backend_pid()`: A — 32923, B — 32924.

| Эксперимент | Изоляция | Наблюдаемый эффект | Способ исправления |
|---|---|---|---|
| Потерянное обновление | READ COMMITTED | Оба прочитали 10, оба записали 9; итог 9 при двух попытках уменьшения; version = 2 | Атомарный UPDATE или FOR UPDATE до вычисления |
| SELECT FOR UPDATE | READ COMMITTED | B ожидает A; после уменьшений получено 8 | Вычислять новый остаток после получения блокировки |
| Атомарное резервирование | READ COMMITTED | Из остатка 1 первый запрос получил 0, второй изменил 0 строк | `UPDATE qty=qty-1 WHERE qty>0 RETURNING qty` |
| Неповторяемое чтение | READ COMMITTED | A прочитал 10, после COMMIT B прочитал 9 | При необходимости единого снимка использовать REPEATABLE READ |
| Повторяемое чтение | REPEATABLE READ | A прочитал 10 и 10, после своего COMMIT увидел 9 | Снимок сохраняется в пределах транзакции |
| Фантом | READ COMMITTED | Повторный COUNT движений изменился с 0 до 1 после INSERT и COMMIT B | REPEATABLE READ для стабильного снимка |
| Взаимная блокировка | READ COMMITTED | Две транзакции захватывают товары в разном порядке; одна прервана с 40P01 | Единый порядок захвата строк, короткие транзакции, повтор после отката |

При ожидании B наблюдался `wait_event_type = Lock`; `pg_blocking_pids` указал PID сеанса A. При втором атомарном UPDATE после ожидания предикат `qty > 0` проверен на обновлённой версии строки, поэтому отрицательный остаток не возник.

Полученное сообщение PostgreSQL:

```text
ERROR:  40P01: deadlock detected
DETAIL:  Process 32924 waits for ShareLock on transaction 830; blocked by process 32923.
Process 32923 waits for ShareLock on transaction 831; blocked by process 32924.
HINT:  See server log for query details.
```

В обоих сеансах после опыта выполнен ROLLBACK. Исходные значения восстановлены (`restored = true`), тестовое движение удалено. Схема Olist использовалась только для чтения.

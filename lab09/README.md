Карпов Андрей Сергеевич, ИНБО-20-23. Вариант 9.

Исходное отношение:

`dispute_flat(dispute_id, order_id, customer_id, customer_city, status_code, status_name, message_id, created_at)`.

## Функциональные зависимости и ключ

Из бизнес-правил задания получены зависимости:

```text
dispute_id → order_id, customer_id, status_code
customer_id → customer_city
status_code → status_name
message_id → dispute_id, created_at
```

Замыкание `{message_id}` сначала включает `dispute_id, created_at`, затем `order_id, customer_id, status_code`, затем `customer_city, status_name`. Получены все атрибуты, поэтому `message_id` — потенциальный ключ. Он минимален: замыкание пустого множества не содержит атрибутов. Любой ключ обязан содержать `message_id`, поскольку он не встречается справа ни в одной заданной зависимости. Следовательно, других минимальных ключей в заданном наборе ФЗ нет.

Замыкание `{dispute_id}` равно `{dispute_id, order_id, customer_id, customer_city, status_code, status_name}` и не содержит сообщения и его даты. Замыкания `{customer_id}` и `{status_code}` соответственно равны `{customer_id, customer_city}` и `{status_code, status_name}`.

Частичных зависимостей от ключа нет: ключ одноатрибутный. Транзитивные зависимости присутствуют: `message_id → dispute_id → order_id, customer_id, status_code`, а также цепочки через `customer_id` и `status_code` к городу и названию статуса. Одноатрибутный ключ не гарантирует 3НФ.

## Аномалии плоской таблицы

| Операция | Аномалия |
|---|---|
| INSERT | Нельзя сохранить новый статус или спор без сообщения, не вводя фиктивный message_id |
| UPDATE | Название статуса повторено в каждой строке сообщения; частичное обновление создаёт разные названия для одного status_code |
| DELETE | Удаление последнего сообщения спора удаляет единственную запись о споре; может исчезнуть и последняя запись о статусе |

## Последовательная декомпозиция

1. **1НФ.** Все значения атомарны, одна строка соответствует одному сообщению; ключ — `message_id`.
2. **2НФ.** Разбиение не требуется: отсутствуют зависимости от части потенциального ключа.
3. **3НФ, первый шаг.** По `customer_id → customer_city` выделяется `Customers(customer_id, customer_city)`. Город удаляется из остаточного отношения; его связывающий атрибут `customer_id` сохраняется.
4. **3НФ, второй шаг.** По `status_code → status_name` выделяется `Statuses(status_code, status_name)`. В остаточном отношении остаётся код статуса.
5. **3НФ, третий шаг.** По `dispute_id → order_id, customer_id, status_code` выделяется `Disputes(dispute_id, order_id, customer_id, status_code)`. Остаток — `Messages(message_id, dispute_id, created_at)`.

Получены четыре отношения `lab.nf_9_customers`, `lab.nf_9_statuses`, `lab.nf_9_disputes`, `lab.nf_9_messages`. Для каждой исходной нетривиальной ФЗ её детерминант является ключом соответствующего итогового отношения; все четыре находятся в НФБК. Все исходные зависимости сохранены внутри отдельных отношений, поэтому проверяются без JOIN.

На каждом бинарном разбиении пересечение содержит детерминант, который определяет всё выделенное отношение: соответственно `customer_id`, `status_code`, `dispute_id`. Это условие соединения без потерь. Последовательность таких разбиений обеспечивает восстановление исходного отношения без ложных строк.

Новых бизнес-зависимостей, например уникальности `status_name` или `order_id → dispute_id`, не добавлено. Составной `UNIQUE(dispute_id, message_id)` ограничивает суперключ, уже уникальный по `message_id`, и не меняет результат нормализации. PK обеспечивают уникальность ключей, FK связывают сообщения со спорами, а споры — со справочниками.

## Тестовые данные

Пять строк плоского примера содержат три спора, три покупателя и три статуса; у первых двух споров по два сообщения. После декомпозиции — 3 строки в каждом справочнике и таблице споров, 5 сообщений. Названия `Открыт` и `На рассмотрении` хранятся по одному разу вместо двух. В SQL есть восстановление JOIN и EXCEPT-проверка в обе стороны.
